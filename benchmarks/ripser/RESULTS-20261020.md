# ripser vs ripser++ -- the benchmark tables of 2026-10-20

The raw tables of the head-to-head between `canns_lib.ripser` and
[ripser++](https://github.com/RustParallel/ripser) on the 1200x1200 ASA
matrix and on the 97 real grid-cells matrices.

**WHERE THEY LIVE.** The tables themselves are NOT in this repository:
`.gitignore` excludes `benchmarks/ripser/results/` ("# Benchmark
results"), so the raw data stays out of the history. The delivery
directory holds both the scripts and the tables, and this file is the map
between them -- the table, what it holds, and which checker guards it.

**The CSVs are the only data source.** `RIPSER-BENCH-20261020.md` (in the
delivery directory, next to the tables) is a view of them: every number in
the report can be pointed at a row of one of these tables, and each table
has a checker that recomputes the verdicts and carries negative
self-tests, so a table that has been edited by hand cannot pass.

The benchmark runs on a remote host (the machine does the work; the local
checkout only carries the code). `../build_and_h2h.sh` builds the
comparison sites; the `check_*.py` scripts below are the checkers.

## How a table knows it was measured on a quiet host

The benchmark host is shared, and a measurement taken while somebody
else's job is running is not a measurement of the code. On this host a
neighbour's job moved a head-to-head ratio by up to 40% and flipped its
sign, so the tables carry their own evidence that the host was quiet.

**The evidence is the foreign CPU load, not the load average.** The load
average counts the measurement itself -- the reduction runs on the host
with one thread per core, and the measurement's own footprint put the
load average at 3.1 on a 16-core box -- so a threshold on it has to clear
the experiment's own footprint, and a neighbour's two-core job then hides
underneath it. Both failure directions were observed: a threshold of 1.5
discarded a batch whose busiest reading was 2.73, and a threshold of 3.0
would not have noticed a two-core neighbour at all. Instead, every
process's CPU time is read from `/proc`, the ones owned by another user
are summed, and the result is a number of *cores used by others*,
recorded on every row (`foreign_cpu.py`). Ours is excluded by
construction, so the reading needs no allowance for how busy the
experiment is, and the checkers require it to be below a quarter of a
core.

**The recorded number is the MEAN over the row, not the peak.** A
neighbour's eight-core job for the whole of a run shows up as eight; one
for a tenth of it as 0.8; a desktop compositor that used one core for
half a second out of a two-minute measurement shows up as 0.004, which is
what it is worth. The largest rate in any half-second window is
recorded beside it (`foreign_max`) as a diagnostic, but it is not the
gate -- gating on the peak throws away long measurements over sub-second
blips, and it did: a batch of clean measurements was discarded over one
0.987-core blip from the machine's own desktop session.

**PID reuse.** The reading is two snapshots half a second apart, and a
process that exits in between can have its pid handed to another
process; the difference of the two tick counts is then meaningless and
can be a whole core out of nothing. Every process is therefore
identified by its start time as well as its pid, and a recycled pid is
never compared with itself.

**The second line of evidence is the numbers themselves.** The same table
is measured more than once on a quiet host and the copies are compared
cell by cell (`cross_batch.py`): a neighbour's job would not make two
independent measurements agree. The host's accounting and the numbers
are independent of each other, so a table carrying both is much harder
to argue with than one carrying a threshold.

⚠ **A threshold change needs the script restarted.** A running `bash`
script does not re-read its own file, and a variable is bound when the
script starts -- so editing the threshold in the file on disk does not
change the behaviour of the instance that is already running. This is not
hypothetical: a batch of clean measurements was discarded by a threshold
that had been changed on disk but not in the running process.

⚠ **The gate is against the shared host, not against ourselves.** It
sees other users' processes; our own concurrent work would be invisible
to it, and is prevented by discipline (one measurement at a time) rather
than by the gate.

## Reading the barcode comparison

An md5 of the bar values is **not** comparable across the two
implementations: ripser++ prints its intervals with 6 significant digits,
so its values carry up to ~5e-6 relative rounding against ours. The
comparison is therefore numeric -- exact equality of the per-dimension bar
counts plus a greedy nearest-neighbour match of the bars with a 1e-5
relative tolerance. The md5 columns are over OUR full-precision bars only,
so they are regression fingerprints for our own runs.

Where the two sides disagree, a third implementation (GUDHI 3.13.0) is run
on the same matrix as an oracle, and the verdict records who it agrees
with. The verdict vocabulary is closed:

- `SAME_BARCODE` -- the two sides agree on every bar;
- `ORACLE_SUPPORTS_OURS` -- they disagree, and GUDHI agrees with us;
- `ORACLE_SUPPORTS_RIPSERPP` -- they disagree, and GUDHI agrees with
  ripser++ (a failure: we would be the odd one out);
- `BARCODE_MISMATCH` -- they disagree and no oracle settled it (a failure).

## Reproducing

```bash
# on the benchmark host, with the two builds installed as "sites"
python nsfix_ab.py       --out nsfix_ab.csv
python clean_h2h.py      --out clean_h2h.csv
python filtration_sweep.py --out filtration_sweep.csv
python validate_gridcells.py --site <site> --cells 0 --out gridcells_validation.csv

# the checkers
python check_nsfix_ab.py nsfix_ab.csv
python check_clean_h2h.py clean_h2h.csv
python check_filtration_sweep.py filtration_sweep.csv
python check_validate_gridcells.py gridcells_validation.csv --self-test
python check_bounds_ab.py bounds_ab.csv --gridcells bounds_gridcells_ab.csv --self-test
python check_standard_bench.py standard_bench.csv --self-test
python check_gridcells_bench.py gca_results_final.csv --self-test
python check_characterize_gridcells.py characterize_gridcells.csv --self-test
python check_scale_scan.py scale_scan.csv --self-test
python check_characterize_gridcells.py characterize_gridcells.csv \
    --sidecar characterize_gridcells.provenance.json --self-test
```

Every checker prints the denominator it computed itself and the names of
the cells that are missing, so a partial table cannot be read as a
complete one.
